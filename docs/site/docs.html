Documentation

cinzel converts CI/CD pipelines between HCL and YAML. Each platform has its own HCL.

Install

A single binary. macOS, Linux and Windows.

$ brew tap yldio/cinzel && brew install --cask cinzel
$ go install github.com/yldio/cinzel@latest

Converting your current CI/CD

Point unparse at a pipeline you already run. Nothing is written to your YAML. 

$ cinzel github unparse --output-directory ./cinzel
$ cinzel gitlab unparse -f .gitlab-ci.yml --output-directory ./cinzel

Edit the HCL to tailor to your preference, then convert it back: 

$ cinzel github parse -d cinzel
$ cinzel gitlab parse -d cinzel

Or use --dry-run to print the result instead of writing it.

github unparse reads .github/workflows on its own. It is the only place GitHub reads a workflow from, so referencing it with -d/--directory is never required. Pass one or more -d/--directory for including folders holding your composite actions as an example.

Where files live

A workflow has one home. An action can sit anywhere, so its HCL records where.

DocumentWritten to
workflow<output-directory>/<filename>.yaml, normally .github/workflows
composite action<path>/<filename>/action.yml, against the root — or under --output-directory when that is given
GitLab pipeline<output-directory>/.gitlab-ci.yml

Unparse fills in an action's path from wherever it found the file. So if you keep actions in actions-x and actions-y, one run each way puts them all back where they started.

By default an action goes where its path says. With path = "actions-x" you get actions-x/setup/action.yml, starting from the repository root. Add --output-directory out and you get out/actions-x/setup/action.yml instead. The flag moves everything under one directory, workflows included.

unparse

YAML → HCL. The direction you start with.

$ cinzel github unparse -d actions-x -d actions-y -r --output-directory cinzel

You never need -d for workflows. cinzel reads .github/workflows on its own whenever it is there. Use -d for composite actions instead, once for each folder you keep them in, and add -r so it looks inside those folders — an action file lives a level down, at actions-x/setup/action.yml.

When a file cannot be converted

If a YAML file is not a workflow, an action or a set of steps, cinzel skips it and warns you which one it skipped. Leaving a dependabot config or an issue template in the same folder is fine.

If it is one of the three and then fails to convert, the whole run stops and nothing gets written — not even the files that converted before it. Your tree is left as it was, and the error tells you which file broke and why.

parse

HCL → YAML. The direction that produces what runs.

$ cinzel github parse -d cinzel

One --directory. A recursive read merges every file into one body, so references cross files freely and a second root would be the same body spelled differently.

Comments survive the trip in both directions and in all three positions — above a block, beside a value, closing a body.

One does not: the comment above env, with, outputs or secrets. Each becomes one HCL block per key, so the mapping has no block of its own, and writing the comment above the first block would make a note about the whole set read as a note about one member. Unparse drops it and prints where it was, as file:line: path. permissions, defaults and concurrency stay a single block and keep theirs, as do the comments on the mapping's own keys.

Generated markers

Every file parse writes opens with three lines:

# generated-by: cinzel
# cinzel-provider: github
# cinzel-source: cinzel/ci.hcl

They are what lets a later run recognise its own output and delete what it no longer writes, which is how a renamed workflow's old YAML gets cleaned up. A file without them was written by hand and is never touched.

diff

Reports what parse would change, and writes nothing. Built to fail a build. 

$ cinzel github diff
$ cinzel gitlab diff
ExitMeaning
0The committed YAML is exactly what the HCL produces.
1Something drifted. Every file is named, with the lines that differ.
2cinzel could not work it out — unreadable HCL, a missing directory.

It also reports a file parse would delete, which is what a renamed workflow leaves behind:

.github/workflows/ci.yaml differs
@@ -10,7 +10,7 @@
 jobs:
   build:
-    runs-on: ubuntu-24.04
+    runs-on: ubuntu-latest
     steps:

would delete: .github/workflows/old-ci.yaml (generated by cinzel, no longer written)

Diff summary: 3 checked, 1 differ, 0 would be created, 1 would be deleted

Line endings are normalised before comparing: generated files are written with LF and a Windows checkout converts them, so a byte-exact check would fail every file there.

pin and upgrade

GitHub only. Operates on the HCL, not the YAML.

$ cinzel github pin              # every tag becomes the SHA it points at
$ cinzel github upgrade          # bump to latest, then pin
$ cinzel github upgrade --parse  # and regenerate the YAML

The tag stays on the line it pinned:

uses {
  action  = "actions/checkout"
  version = "3d3c42e5aac5ba805825da76410c181273ba90b1" # v7.0.1
}

Both exit non-zero when an action could not be resolved, so a CI step running either fails on a workflow still holding an unpinned one. No token is needed for public actions; GITHUB_TOKEN raises the rate limit from 60 an hour to 5000.

Run parse afterwards, or the YAML still carries the old tags.

assist

A pipeline from a prompt, through the same conversion path. Both providers. 

$ cinzel github assist --prompt "golang PR with tests and linting"

Output goes to a timestamped folder under cinzel/assist, one per prompt. Blocks matching HCL you already have become a // reuses: comment rather than a duplicate, and generated actions are pinned to SHAs on the way out.

Refine what came back:

$ cinzel github assist --refine "add a slack notification on failure"
$ cinzel github assist --refine "add caching" --from 20260317-150405

The API key comes from the environment. Set ANTHROPIC_API_KEY or OPENAI_API_KEY. cinzel init writes a config holding your default provider and model, and deliberately does not hold a key: that file lands on disk and gets swept into a backup of your home directory.

init

Writes the configuration assist reads: your default AI provider and the model to use for each. 

$ cinzel init

It asks which provider to default to and writes the file to your OS configuration directory with 0600 permissions. Nothing else needs it — parse, unparse, diff, pin and upgrade all run without any configuration.

It deliberately holds no API key. That file lands on disk and gets swept into a backup of your home directory, so the key belongs in the environment instead.

Shared flags

parse and unparse both take these.

FlagDoes
--file, -fRead one file. A directory is refused; --directory is for that.
--directory, -dRead every matching file in a directory. Not with --file. Repeatable on unparse.
--recursive, -rWalk subdirectories. Needed for composite actions.
--rootResolve every path against this directory. Not with --output-directory.
--output-directoryWhere to write. Parse defaults to .github/workflows, unparse to ./cinzel.
--dry-runPrint instead of writing.
--ymlParse only: write .yml instead of .yaml.

--root

Relocates a whole run — what is read, what is written, and the defaults under both. It must be a path relative to where cinzel runs: 

$ cinzel github parse --root project-x
# → project-x/.github/workflows/ci.yaml
# → project-x/actions-x/setup/action.yml

Setting it together with --output-directory is an error rather than a precedence rule: the two answer the same question, one for the run and one per document type.

.cinzelrc.yaml

The flags you always pass, in a file you commit.

github:
  parse:
    directory: ./cinzel
    output-directory: .github/workflows
    recursive: true

A flag on the command line still wins. It covers parse and unparse only, per provider — assist, pin, upgrade and init ignore it. Keys are file, directory, output-directory, yml and recursive; yml only affects parse, so it is accepted and ignored under unparse. Anything else prints a warning and is skipped. yml and recursive are booleans, written bare rather than quoted.

Paths must be relative and written with forward slashes. The file is read on every machine that checks the repository out, so an absolute path or a leading ~ is refused with an error naming the key.

The HCL: GitHub Actions

Steps and jobs are top-level blocks, referred to by name rather than nested. 

workflow "ci" {
  filename = "ci"
  name     = "CI"

  on "push" {
    branches = ["main"]
  }

  jobs = [job.build_and_test]
}

job "build_and_test" {
  id = "build-and-test"

  runs_on {
    runners = "ubuntu-latest"
  }

  steps = [step.checkout, step.test]
}

Things that catch people out

  • Labels cannot hold a -. So build-and-test is written as job "build_and_test" with id = "build-and-test" beside it. The id is what goes back into the YAML.
  • needs: is spelled depends_on, and holds job.<label> references.
  • ${{ }} doubles its $. ${{ github.sha }} becomes $${{ github.sha }} so HCL does not interpolate it. Never write the escape by hand — the converter owns it both ways.
  • ignore_id = true means the step had no id:. Parse gives a step its block label as an id by default; a step converted from YAML that never had one carries this so it does not gain one.
  • Two workflows cannot share a name, and neither can two actions. A workflow and an action may: they are written to different files.

Composite actions

The other GitHub document type. Uses input, output and runs blocks, and shares the same step blocks a workflow uses. 

action "setup" {
  filename = "setup"
  path     = "actions-x"
  name     = "Setup"

  description = "Installs the toolchain"

  input "node_version" {
    default  = "20"
    required = true
  }

  runs {
    using = "composite"
    steps = [step.setup_node, step.build]
  }
}

filename is the action's own folder and path the folders above it, so this writes actions-x/setup/action.yml. An action with no path goes under the output directory, as it always did.

A path is fenced the way filename is: relative, no .., nothing absolute. runs.using may be composite, node20 or docker.

The HCL: GitLab CI/CD

A different schema. One pipeline, with jobs, templates and includes — not GitHub's blocks. 

stages = ["build", "test"]

job "build_app" {
  id = "build-app"

  image  = "golang:1.26"
  script = ["go build -o app ./..."]
  stage  = "build"
}

job "test" {
  depends_on = [job.build_app]

  rule {
    if = "$CI_PIPELINE_SOURCE == \\"merge_request_event\\""
  }

  script = ["go test ./..."]
  stage  = "test"
}
  • Repeatable things are blocks; everything else is an attribute. rule {}, cache {}, service {} and include {} can appear more than once.
  • A template is a hidden job. template "go_base" is .go_base: in YAML, and extends refers to it as template.go_base.
  • $ doubles up. ${CI_COMMIT_BRANCH} becomes $${CI_COMMIT_BRANCH}. A bare $CI_PIPELINE_SOURCE with no braces needs no escaping.
  • An empty or null keyword is kept, not dropped. GitLab reads cache: [] as "clear what this would inherit", which differs from leaving the keyword out.

What gets checked

The same rules apply in both directions, so HCL that converts is HCL that converts back.

  • A workflow needs at least one on trigger and at least one job.
  • A normal job needs runs_on and at least one step. A reusable one must have neither.
  • An action needs name and runs.using.
  • permissions scopes and levels are checked against the known set.
  • on.schedule crons are checked for the five-field form and sane ranges.
  • A step's uses must read as owner/repo@ref, ./path, $/path or docker://image. A $/ reference carries no version: GitHub resolves it at the commit the caller runs from, and it is not available on GitHub Enterprise Server.

A file failing one of these stops with an error naming the problem, rather than writing YAML the platform would reject. Converting a keyword the schema does not declare is an error too, not a silent pass-through.

Round trips are semantically stable, not byte-stable. Key order and formatting normalise even where the meaning is untouched. Nothing is added that the HCL did not say: a workflow declaring no permissions is written without one.

In CI

Once the HCL is the source, an edit to the generated YAML goes away at the next parse. diff catches it at the time. 

- name: Pipelines match their HCL
  run: cinzel github diff

This repository runs exactly that on every pull request, which is also how the command gets exercised outside its own tests.
